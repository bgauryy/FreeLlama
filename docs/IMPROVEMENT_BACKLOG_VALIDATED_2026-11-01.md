HEAD is `e718d8ad7af6af6e2a05ee6d3fc075dec9e8216f`; substantial staged work is present. References describe this inspected snapshot and can move as other work continues.

The earlier list was too broad in places. Adaptive concurrency, context profiles, configuration provenance, a status UI, paged result retrieval, embedding identity checks, evaluation infrastructure and many concurrency tests already exist. The remaining work must build on them. A persistent vector index does not currently exist, so missing index persistence is not an existing product correctness bug.

## Rating and evidence rules

Importance rates the **remaining work**, not the current feature's quality or a measured speedup: **5** release/safety gate or highest corrective priority; **4** high-value next work; **3** useful targeted improvement; **2** optional extension; **1** experimental or defer. Conditional priorities are identified explicitly. Hardware-specific work rises in priority only when that hardware is a supported deployment target.

- **Bug:** a concrete implemented path contradicts the intended behavior or makes an unsupported claim. Static code evidence is distinguished from a reproduced failure.
- **Risk:** a credible failure boundary without a reproduced physical failure.
- **Validation:** functionality exists, but the required measurements or acceptance run are incomplete.
- **Partial/feature:** existing foundations need a specific extension.
- **Existing:** close the original build task; keep only a narrowly defined validation or presentation delta.
- **Extra/research:** optional new scope, not a repair to current functionality.

Six parallel read-only reviews covered the 50 items. The root checked the main findings in source. Octocode structural search located the awaited native poll; LSP references failed with `executionFailed`, so direct source search was used rather than inferring absence. Two isolated JavaScript checks executed current source with mocked calls, no sockets or models. This review did not rerun the production gate, change production code, pull/load/unload models, or modify Ollama settings. It creates this report and its documentation-index link.

### Concrete failure boundaries

**Memory configuration (#10).** [Setting resolution](../packages/rust-core/src/platform/ollama_env.rs#L149) correctly labels process, launchd and FreeLlama-environment sources. But [initialization](../packages/rust-core/src/platform/mod.rs#L298) and [refresh](../packages/rust-core/src/platform/mod.rs#L188) pass value-only `lookup` results into [RuntimeHints](../packages/rust-core/src/platform/footprint.rs#L65). A fallback `OLLAMA_FLASH_ATTENTION=1` plus `OLLAMA_KV_CACHE_TYPE=q4_0` can therefore reduce estimated KV bytes to 25% even when that environment was not attributed to the local Ollama process. The concrete admission concern is a local endpoint whose process cannot be inspected. Remote work already returns `host_memory_not_applicable` in [requirement](../packages/rust-core/src/platform/footprint.rs#L272), so this is not a claim that remote VRAM is charged to local RAM. Preserve fallback hints diagnostically; do not use them as evidence for a downward memory adjustment. Configured FA also does not prove a backend accepted it.

**Cancellation (#3).** [Abort handling](../packages/mcp/src/job-progress.ts#L268) dispatches cancellation immediately, but [polling](../packages/mcp/src/job-progress.ts#L298) awaits GET before reaching the cancellation-report limit. The existing [unit test](../packages/mcp/test/unit/job-progress.test.ts#L190) manually finishes that poll before expecting rejection. An isolated execution of this source returned `{after_abort_ms:5200,cancellation_calls:1,caller_settled:false}` with an acknowledged cancellation. Completing the mocked GET then released the caller. This demonstrates caller latency, not failure to send cancellation or proof that Ollama continued physically executing.

**Unload reconciliation (#7).** [Automatic eviction](../packages/rust-core/src/platform/execution/memory.rs#L524) puts failed exchanges in `failed`, then confirms only `requested` (successful HTTP exchanges) at line 527 before releasing claims. [Managed explicit unload](../packages/rust-core/src/platform/execution/mod.rs#L227) performs confirmation even after a failed exchange but discards it at `posted?` on line 234. [Raw explicit unload](../packages/rust-core/src/proxy/mod.rs#L925) already keeps ownership during post-error confirmation. Extend the narrow inconsistent paths; do not rebuild unloading or infer that an HTTP error proves the request was never accepted.

**Slow readers (#33).** Before response headers, [forwarding](../packages/rust-core/src/proxy/mod.rs#L786) races runner readiness. After headers, the readiness future is polled only by [AdmittedBody::poll_frame](../packages/rust-core/src/proxy/admission.rs#L258). If downstream demand stops polling the body, readiness observation and load-lock release also stop. Execution/use ownership should remain through EOF/drop; transition readiness should not depend on the consumer draining the answer. A controlled slow-reader regression is still required to characterize HTTP-level behavior.

**Benchmark integrity (#5/#8).** [asked](../scripts/local-test/rivals.mjs#L40) retries status 0, 429 and 503 without consulting execution outcome. Running that exact function with mocks produced two submissions for both a network error and a `503` receipt containing `execution_outcome:"unknown",retry_safe:false`. This is a local benchmark-harness defect; the repaired production MCP research retry path is separate. The harness also [resumes by group/model name](../scripts/local-test/rivals.mjs#L543), [stores exceptions under a different key](../scripts/local-test/rivals.mjs#L561), and [exits zero with unfinished or failed work](../scripts/local-test/rivals.mjs#L573). Its [report](../scripts/local-test/rivals.mjs#L505) hardcodes hardware/version and its [reload label](../scripts/local-test/rivals.mjs#L481) uses a timer threshold. Fix evidence collection before promoting its outputs to model defaults or performance claims.

**Catalog fit (#4).** [MCP](../packages/mcp/src/model-catalog.ts#L22) and [CLI](../packages/cli/src/requests.rs#L188) compare current host available bytes with static `memory_gb` from the model catalog. This ignores requested context, reservations, resident reuse and device topology. The MCP text says “fits now/no room now.” Label this as an advisory historical estimate or obtain task-specific resource assessment from Rust; even preview remains a snapshot, not a reservation.

**Durable-key ordering (#6).** [Key creation](../packages/rust-core/src/platform/job_journal.rs#L87) syncs a temporary file, hard-links the final name and returns without an explicit parent-directory sync. Atomic publication and power-loss durability are different requirements. Missing-key effects are already documented in [Deferred jobs](DEFERRED_JOBS.md#request-hashes); no lost key or duplicate execution was reproduced here. Verify platform-appropriate durable publication before accepting keyed work, and test backup/recovery with the matching secret.

**Archive growth (#34).** [ResponseStore](../packages/mcp/src/response-store.ts#L62) appends entries and [tombstones](../packages/mcp/src/response-store.ts#L187), then [reads the entire index](../packages/mcp/src/response-store.ts#L96). The live payload budget excludes that index, and the current session directory is retained. The separate [usage ledger](../packages/rust-core/src/store/usage.rs#L23) intentionally never deletes history. Do not conflate either with the bounded durable-job journal. Compaction/rotation must preserve audit history and concurrent readers/writers.
